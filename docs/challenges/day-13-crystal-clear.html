Today's layer: Crystal, and ZERO new slot shapes

The day's new toolchain is Crystal (LLVM-backed, compiles to a native ELF). Fingerprint evidence from the d13 member:

  • readelf -sW / strings: Crystal's own symbol convention, a leading * plus namespaced method - *Crystal::System::print_error, *Crystal::Iconv, *Crystal::FdLock, *Crystal::EventLoop::Polling - 470 *-prefixed symbols out of 1,520 total.
  • Crystal's runtime type names appear verbatim: Crystal::DWARF::Abbrev, Crystal::DWARF::LineNumbers::Row, Crystal::EventLoop::Polling::Event, Crystal::PointerLinkedList, Crystal::ELF::SectionHeader (Crystal ships its own ELF/DWARF reader for backtraces - a very distinctive tell).
  • Not stripped, has_symtab=true; no gopclntab (not Go), no C++ typeinfo/vtables (not the Itanium-mangled C++ path), libgcc_s.so.1 + libc.so.6 only.

The important finding: the d13 block introduced no new slot. Its ten answer ids are all shapes the adapter already answers:

Lessons / reusable notes

  • Crystal's giveaway is the *-prefixed mangled symbol plus its in-binary DWARF/ELF reader classes (Crystal::DWARF::*, Crystal::ELF::*). Added to the lane's toolchain fingerprint list.
  • Two days running with zero new slots. The cumulative-bundle + fixed-10-slot structure is stable enough that the right reflex on this lane is "run the banked adapter, then check only whether the new dNN block introduced an id shape that is not already covered" - not "re-analyse the binary".
  • A prompt sentence that sounds like a new task ("follow the DNS labels") can simply be flavour text for existing HCFG keys. Check the answer ids before believing the prose.
