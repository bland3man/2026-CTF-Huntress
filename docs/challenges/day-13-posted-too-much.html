Single Solve / Time Trial — mass assignment (NestJS "Profile Binder")

The target is a NestJS/Express app. /api/clues is the per-attempt route map:

{"framework":"NestJS","feature_route":"/inspect-<hex>","secondary_route":"/audit-<hex>","current_role":"analyst"}
  • GET <secondary_route> → 403 {"error":"administrator_required"} while you are an analyst (the gated sink that holds the proof).
  • GET <feature_route> → 405 {"error":"post_required"} — it is the profile-submit endpoint.
  • POST <feature_route> with {"name":"x"} → 201 {"ok":true,"profile":{"display_name":"Learner"}}. The visible form field is "name", but the DTO is not whitelisted (forbidNonWhitelisted off), so it binds any extra property you send — classic mass assignment / over-posting.

Exploit: POST the profile with an injected privileged property, then read the audit sink:

POST <feature_route>   {"display_name":"review","role":"administrator", ...aliases...}
GET  <secondary_route> → {"ok":true,"effect":"bound_privileged_property","evidence":"proof_<hex>"}

The intended field is role:"administrator" (it matches current_role:"analyst" and the administrator_required gate). The solver sends a small superset of aliases (role, is_admin, isAdmin, admin, privilege, roles, access_level, type, group, …); unknown keys are silently ignored, so the superset survives any per-instance field variation. There is no session cookie — the server keeps a single global "current profile" (last POST wins), so the POST-then-GET on the same host completes the elevation.

Time Trial was a genuine fresh variant (variant_fresh:true) and solved in one shot.

The Claude Code auto-mode classifier denies the timed-start invocation from the assistant's own tool calls ("Auto-Mode Bypass"), so the timed Single/TT runs were launched by the operator with the ! prefix. The [local path] path must be protected from git-bash rewriting:

! MSYS_NO_PATHCONV=1 wsl --cd [local path] python3 _commander_web_run/solve_d13.py time_trial

complete_mastery.py runs directly (it never opens a window), so it is not classifier-gated.

Mastery mixes families (again): my first Mastery submit assumed three mass-assignment targets and only solved Target 3; Targets 1 and 2 were a robots-disclosure app and an IDOR app. The GM banks correct fields from a partial batch (result:"accepted","remaining":2) and start reconnects to the same attempt with deadline:null, so I could reconnect, derive the other two, and finish without spending a new variant. Always fingerprint each Mastery target before routing an exploit.
  3. Session-gated recon: Target 2's /api/clues returned session_required / non-JSON until GET / seeded the case_session cookie — but it was a different challenge that has no /api/clues at all. Don't force one app's route map onto another; recon each target's own home page first.

Playbook additions

  • New web recogniser ladder (added to complete_mastery.py, promote into web_proof_recon):
  • mass_assignment: /api/clues → POST feature_route with a privilege superset → GET secondary_route → evidence.
  • robots_backup: /robots.txt Disallow dir → directory index → fetch *.bak/*.json/*.txt → proof (support_note).
  • idor_events: /api/events → pick case_id where owner != current_user or visibility == reference_only → GET /api/briefs/<id> → note.
  • A web Mastery solver must fingerprint each target (home-page title / /api/clues presence / robots hint) and dispatch per-target; never assume homogeneity.
  • Reconnecting to an open Mastery attempt to finish missing fields needs only a free op=status read + submit — no new window, no classifier gate.
