Triage

  • RULE 2 (file type): .zip -> carving/crypto. zipinfo -v showed AES encryption, so a password was needed before anything else.
  • RULE 3 (theme): "Mangled" = C++ name mangling. The two members day01-c.elf (C) / day02-cpp.elf (C++) make the theme explicit; the C++ binary carries mangled symbols (_ZN15DiscoveryEngine...), the C binary does not.
  • Primary specialist domain: malware_re (solved inline - small, static, deterministic).
  • Hypotheses: (H1) flag hidden in a binary section/string; (H2) flag produced by running with the right input; (H3) recover an encoded malware config and submit a field to the GM. H3 proved correct.

Investigation

  1. Password. unzip refused ("need PK compat v5.1" = AES). Tried a short thematic wordlist with 7z t -p<pw>; infected (the classic malware-zip password) worked: 
    7z t -pinfected mangled.zip   # Everything is Ok
7z x -pinfected -y mangled.zip
  2. Identify. Both are ELF 64-bit LSB executable, x86-64, not stripped.
    • day01-c.elf: function recover_code (returns 0x1fa4 = 8100), custom section .huntress = BR01-CATALOG-000. A minimal C "catalog" counterpart.
    • day02-cpp.elf: C++ class DiscoveryEngine with score(const char*) const, family() const; RTTI type-name string 15DiscoveryEngine; a printf emitting a huntress.binary.dynamic_trace.v1 JSON.
  3. Dynamic trace (run). Running day02-cpp.elf prints: 
    {"schema":"huntress.binary.dynamic_trace.v1","branch":"success","event_count":6,
 "campaign":"BR02-000","family":"system_information_discovery","rtti":"15DiscoveryEngine"}

    main reads env HUNTRESS_HOST_MODEL; DiscoveryEngine::score returns 6 for workstation, 3 for analysis (-> branch decoy), 1 otherwise (-> failure). family = system_information_discovery maps to MITRE ATT&CK T1082. No flag in the trace.

  4. The mangled config (key step). readelf -S revealed a non-standard section **.hcfg** in day02-cpp.elf (the "HCFG" magic also shows in strings). Dumping it showed an encoded blob with 0x13 used as a field separator and repeated sc 01 03 1c... groups - classic single-byte XOR.
    • Header: 48 43 46 47 | 01 | 31 | ... = magic HCFG, version 01, **XOR key 0x31** (self-describing, byte offset 5).
    • Confirm by known plaintext: 0x13^0x31 = 0x22 ("), 0x0b^0x31 = 0x3a (:), 73 63 01 03 1c -> "BR02-".
    • XOR the section with 0x31:
    {"campaign":"BR02-000","domain":"node-000.day02.example.invalid","ipv4":"198.51.100.40",
 "url":"https://node-000.day02.example.invalid/api/BR02-000","mutex":"Global\\HuntressBR02_000",
 "windows_path":"C:\\ProgramData\\HuntressLab\\day02\\BR02-000.dat",
 "linux_path":"/var/tmp/huntress-lab/day02/BR02-000.dat","service":"HuntressLab-Day02-000",
 "host_model":"workstation"}

    This is the sample's hidden campaign/IOC config - "mangled" twice over: C++ mangled symbols + an XOR-mangled config section.

  5. Flag search (negative, important). Exhaustive strings/section sweep of both binaries (.rodata, .hcfg, .huntress, .comment, symtab, overlay) found no flag{}/huntress{} token. day01-c.elf has no .hcfg. Conclusion: there is no offline flag; the recovered config (or a specific field) is the value to submit to the Game Master - the same dynamic model confirmed on "Half a Turn".

Flag Recovery

  • Source: the .hcfg section of the assigned day02-cpp.elf.
  • Transform: single-byte XOR; key is header byte 5 (0x31 for this copy) - or, attempt-independently, the unique byte that makes the blob decode to JSON whose first key is campaign.
  • Verification: scripts/solve_mangled.py parses the ELF section table directly (no external tools), brute-forces the XOR key by validating the decoded JSON, and reprints the config. Re-running reproduces xor_key: 0x31 and the config above - deterministic and reproducible.

Per-attempt note: the Game Master serves dynamic bytes, so the numbering (BR02-NNN, node-NNN, the IPv4) will differ from this static copy. The solver is written to be attempt-independent; run it on the downloaded attempt binary and submit the field the GM asks for.

Lessons Learned

  • What mattered: readelf -S to spot the non-standard .hcfg section; recognizing single-byte XOR from the regular 0x13 separators; and reading the XOR key straight out of the section header instead of guessing.
  • "infected" remains the go-to password for AES-encrypted malware-lab zips.
  • Theme was literal: "Mangled" = both C++ symbol mangling and an XOR-mangled config. The C++ mangled names (DiscoveryEngine, RTTI 15DiscoveryEngine) are thematic signposts, not the flag.
  • What would have wasted time: deep-reversing the C++ vtable/score logic or the runtime boilerplate - the payload was the data section, not the code (2025 heuristic: inspect suspicious data/strings/sections before reversing runtime init).
  • Negative result is a result: confirming no offline flag exists is what establishes this as a GM-submission challenge, so no fabricated flag is printed.
  • Reusable tool: scripts/solve_mangled.py auto-detects the XOR key and parses the ELF without external tools, so it survives per-attempt variants and timed modes.
