Prompt

An MSBuild project looks like routine build plumbing until you follow its properties into its targets. Recover the property and target flow, compare it with earlier execution chains, and find where a trusted toolchain is doing untrusted work.

The real gap: the marker is wrapped in a host-language comment

Each fixture is an inert MSBuild project that carries the usual HUNTRESS_ANALYSIS_V1 descriptor twice - once in an XML comment and once in a <PropertyGroup> property, which is exactly the "follow its properties into its targets" the prompt points at:

<?xml version="1.0" encoding="utf-8"?>
<!-- HUNTRESS_ANALYSIS_V1:HB64-646a307a66477868626d6431... -->
<Project xmlns="http://schemas.microsoft.com/developer/msbuild/2003">
  <PropertyGroup><HuntressDescriptor>646a307a66477868626d6431...</HuntressDescriptor></PropertyGroup>
  <Target Name="Analyze"><Message Text="Inert analysis fixture" Importance="low" /></Target>
</Project>

The encoding is self-declared by the tag after the marker, and the four fixtures deliberately use one each:

All four tags were already implemented in solve_poly_d8._decode_known. The break was one character class. MARK is

MARK = re.compile(r'HUNTRESS_ANALYSIS_V1:([A-Z0-9]+)-([^\r\n\'"]+)')

which excludes newlines and quotes but not spaces, so inside an XML comment the payload capture kept the comment terminator:

kind= HB64 payload tail= '526b4c6e4e305957646c -->'

bytes.fromhex() then failed, _peel() failed, and desc_of raised unpeelable. The giveaway in the residue was that exactly 3 of the 4 fixtures were unresolved: B64- survived because base64.b64decode stops at the padding and silently ignores the trailing -->. Every earlier day's carrier put the marker in a line comment with nothing after it, so the bug had never fired.

Fix (challenges/_lib/solve_poly_d8.py)

desc_of now sanitizes before decoding and prefers the most complete descriptor:

  1. clean_payload() cuts the capture at the first whitespace and sheds trailing comment closers (-->, ]]>, */, ?>, #>, --).
  2. If that still will not decode, fall back to the <HuntressDescriptor> / <HuntressMaterial> property element - the second copy MSBuild carries.
  3. Among candidates that decode to a v= descriptor, keep the one with the most fields. A payload truncated by the host container still decodes to a leading v=3|language=... fragment, so a field count is what separates a whole copy from a partial one; a first-match-wins rule would have accepted the fragment.

Takeaway for the lane

The carrier format is no longer the interesting variable - every proxy-execution and persistence carrier in the candidate list was already in LANGS. What breaks is the envelope around the marker. Any future carrier whose comment syntax has a terminator (XML/HTML, /* */, <?php ?>, <# #>, Lua --, CDATA) would have hit the same bug, and a base64-tagged fixture will hide it by decoding anyway. The sanitizer plus the property fallback covers that whole class now.
