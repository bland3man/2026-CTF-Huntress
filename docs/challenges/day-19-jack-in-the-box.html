The new layer: a packed overlay, not a section

Every earlier day hid the HCFG config record inside the file - raw in .hcfg, base64 in .rodata, a C const array, a wasm data segment. Day 19 does not: grep -c HCFG on the member is 0, and the section-header table ends at file offset 0x2378 while the member is 11,232 bytes long. The record lives in an overlay appended after the end of the real ELF, which is exactly what "a payload hiding inside this binary, and a little decoder stub wound up to pop it out" means, and why the questions ask for an overlay offset and size for the first time (d19_analysis_overlay_offset, d19_analysis_overlay_size - two brand-new question keys).

The GM states the stub layout in the question text, so nothing had to be hand-traced out of the .text disassembly. At the final occurrence of the magic (PK19 for Day 19, and the question names RS20 for Day 20 - so the magic is data, not a constant):

+0   magic          'PK19' (4 bytes)
+5   k1             u8
+6   k2             u8
+8   packed_len     u32 little-endian
+12  sha256         32 bytes - SHA-256 of the UNPACKED bytes
+44  packed bytes   packed_len bytes, running to EOF

Unpack transform, per packed byte:

plain = ror8(packed ^ k2, 3) ^ k1          ror8(x,3) = ((x >> 3) | (x << 5)) & 0xFF

The unpacked buffer then carries the familiar HCFG record at offset 0: 'HCFG' | version u8 | xor_key u8 | payload_len u16le | crc32 u32le | payload, payload XORed with the one-byte key and parsed as UTF-8 JSON.

What was built

challenges/_lib/autosolve_binary.py (the lane spine was not rebuilt - only the new layer added):

  1. _ror8, _overlay_unpack, _overlay - find the final 4-byte [A-Z]{2}[0-9]{2} magic whose declared length ends exactly at EOF and whose embedded SHA-256 verifies, and return the unpacked bytes. The magic is read from the member, so Day 20's RS20 needs no code change.
  2. config() - after collecting the container's blobs, each blob's verified overlay is unpacked and appended as one more HCFG carrier. The existing _pick_hcfg uniqueness rule still applies, so a second distinct carrier would Hold rather than guess. The d19 member has exactly one.
  3. answer() - analysis_overlay_offset / analysis_overlay_size resolve from _overlay and Hold (never guess) when no SHA-256-verified stub exists.

Supporting files in this folder:

  • scripts/pk19_overlay.py (not found in any source) - standalone, self-documenting unpacker (python3 pk19_overlay.py <member> [MAGIC]).
  • scripts/local_check.py (not found in any source) - offline resolver for every d19_* id through autosolve_binary.answer(), no GM call. Printed 12/12 OK before any submit; a full sweep resolved all 228 fields SURE, 0 probes.
  • challenges/_lib/_test_binary_overlay.py - new lane catalog test, 16 checks, RESULT: PASS: independent struct-based parse vs the adapter on the real member; a re-packed RS20 overlay with different keys; a corrupted SHA-256 and an overlay-less member yielding nothing; and a scan-cost guard. The one real mistake, and the cost

The first implementation sliced the declared payload before bounds-checking its length. Any 4-byte LLDD text in a member looked like a candidate magic, and the 67 MB d08 member matches that pattern about 65,000 times - each match slicing up to 67 MB. The overlay scan took 133.7 s on d08 alone. The Single Solve still graded CORRECT (137.2 s, untimed), but the same run then spent ~10 minutes of CPU on the Time Trial's variant and had to be killed.

Checked before doing anything else: a free op=status on both timed entries returned 409 start_required, i.e. no timed window had been opened and no variant was spent - the stall happened in the pre-start compute. The fix was to test off + 44 + ln == len(data) before touching the payload (the stub runs to EOF by definition) and to search backwards from the last MiB, returning the first verified hit. d08's scan went from 133.7 s to 0.00 s, and all 228 fields now resolve in 1.5 s. The rerun took the Time Trial in 7.1 s and the Mastery in 28.4 s.

Lesson for the lane: a byte-scanning extractor must bounds-check a length field read from untrusted bytes before slicing, and any new scan belongs on the clock-cost guard in the catalog test - a slow extractor is a lost timed window even when every answer it produces is right.
