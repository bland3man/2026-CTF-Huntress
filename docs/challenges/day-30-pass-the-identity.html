What could have been recognized faster (one-glance signals)

  • Title "Pass the Identity" + "delegated service boundary" + "photocopies" = header-trust impersonation. The three-word rule: delegated / on-behalf-of / propagated ⇒ try an unsigned identity header first (one-shot X-On-Behalf-Of, X-Delegated-User, X-Act-As, X-Impersonate, X-Caller, On-Behalf-Of, Remote-User), seeded with every non-caller value out of /api/identities. ~10 s to try, ~0 risk.
  • **/api/clues + framework:"Axum" + identity_directory_route** is the fingerprint. Any time an advertisement endpoint names an identity directory → identity-delegation family. Bank it.
  • **/healthz.profile** is literally the family label on every target in this event: node_http_backup_disclosure, express_idor, flask_sqli, php_lfi, axum_identity_delegation, micronaut_xff_bypass, … The Mastery lane-sampler telegraphs its 5 families in one GET each. Running GET /healthz across all targets BEFORE the battery is a 5-request family-dispatch oracle. Nothing in the current adapter uses this.
  • **result:active, targets:[]** on a web start = still preparing. 1× GM.status recovers them, usually within 30 s of start. Don't let _lfi_handler return {} + wait for the dispatcher to time out at 90 s per target.

What worked

  1. **Fingerprint-gated _tech_pass_the_identity + header ladder** → SS CORRECT in 6.5 s once the technique was in. TT reused it automatically after SS CORRECT → 16 s RANKED.
  2. **GM.status-fallback inside _lfi_handler** when start["targets"] is empty but start["attempt_id"] is set → recovers targets + questions + routes without touching the adapter contract.
  3. Fresh-subprocess fan-out (scripts/target_solve_subprocess.py) that calls urlsplit(target_url) → scheme://netloc first, then runs a 6-family dispatch. This is the pattern from docs/commander/SPEEDUP_PARALLELISM.md: fan-out-then-join with scoped filenames. Zero shared process state, zero scope leakage, hits 100% of the 5 Mastery families this event has thrown.

What didn't work (and why — so we stop retrying them)

  • Parallel-retry inside the same battery. Same URL-folding bug, same 404.
  • urllib direct retry. Same bug.
  • curl subprocess retry inside the same Python. Same bug — subprocess inherits argv, which was already wrong.
  • Longer deadlines. The requests were succeeding at 404; more time didn't help.

Rule for tomorrow: before trying another retry transport, print exactly which URL the technique is fetching to stderr. One line fixes 90% of these.

Single Solve / Time Trial — the "Caller Courier" family

The live target advertises itself at /api/clues:

{"current_role":"analyst",
 "feature_route":"/execute-373d79",
 "framework":"Axum",
 "identity_directory_route":"/api/identities",
 "secondary_route":"/result-31b669"}

/api/identities returns { "caller":"analyst", "records_owner":"executive" } and the two business routes return {"error":"delegated_identity_rejected"} without a delegation header.

A short ladder of common on-behalf-of header names finds the one the Axum middleware trusts: **X-Delegated-User**. One request:

GET /execute-373d79 HTTP/1.1
X-Delegated-User: executive

returns {"effect":"delegated_identity_trusted","evidence":"proof_<32hex>","ok":true}. That proof_<hex> is the single-field answer.

Why it works

The server trusts a plain HTTP header for identity propagation. In a real "delegated service boundary" an identity assertion must be signed and audience- scoped (OAuth2 On-Behalf-Of, mTLS cert passthrough, OIDC token exchange). The app under test blindly reads X-Delegated-User from the incoming request and promotes the caller to that principal — the classic photocopy-identity bug.

Codified technique

Added _tech_pass_the_identity to the lane battery in the per-challenge solver copy (scripts/web_wip.py). Fingerprint-gated on framework == "Axum" + identity_directory_route so it only fires on this family; a short header ladder covers common variants (X-On-Behalf-Of, X-Act-As, X-Impersonate, X-Caller, On-Behalf-Of, …).

The real root cause (lesson)

The in-process techniques saw /robots.txt → 404 on the two "quiet" targets. Not a Cloudflare race, not a scope leak — the dispatcher's URL folding was the culprit:

_lfi_handler, before dispatching

if path: url = base + path.rstrip("/") # routes[].path appended to each target_url


So `_solve_target` sees `https://<host>/HEX_ROUTE/`. Techniques that build
their fetch URL as `target_url.rstrip("/") + "/robots.txt"` end up requesting
`https://<host>/HEX_ROUTE/robots.txt` which is a 404. Techniques that call
`_base_origin(target_url)` first (D27 audit additions) rebuild `scheme://netloc`
and work. On this Mastery that split the 5 targets into "works" (pass_the_identity
Target 5, lfi_viewer Target 4, session_idor_cookiejar Target 2) and "doesn't"
(robots_recon Target 1, breach_search_sqli_union Target 3).

Memory already captured this: `feedback_web_technique_base_rebuild.md`
("Web techniques must rebuild base from scheme+netloc"). This writeup is a
second confirmed hit for that rule.

Repair applied in the clone

  • Added a fresh-subprocess fallback in _lfi_handler after the parallel battery: for each still-unresolved proof-N, spawn python3 scripts/target_solve_subprocess.py <url>. The helper strips the URL back to scheme://netloc via urllib.parse.urlsplit before any request, then runs a family dispatch (robots→backup, Axum identity, PHP LFI, session IDOR with cookie jar, SQLi search, body scan). Isolated process state, no shared web_scope ThreadPool, bounded 90 s per target. Hits every family Mastery has thrown so far.
  • Added a GM.status-recovery line to _lfi_handler for the common case where GM.start's response for mastery/time_trial omits targets[] while a status call returns them.

Both are in scripts/web_wip.py of this challenge folder.

Lessons + D+1

  • Lane-wide: every mastery technique that calls /robots.txt, /api/clues, /healthz, or any absolute path MUST build its base from urllib.parse.urlsplit(target_url) → scheme://netloc. Don't rstrip("/") the dispatcher's folded url. Fix the pattern once in autosolve_web.py so the whole shared battery stops losing variants on routes-bearing targets. (feedback_web_technique_base_rebuild.md — second confirmed hit.)
  • Dispatcher: _lfi_handler should fall back to GM.status(entry) when start["targets"] is empty but start["attempt_id"] is present. Several mastery variants arrive with targets[] absent from the start response and only populated on a later status read. Current code emits _no_live_targets and returns {} → gate_blocked for the whole batch. Easy win, keep it local to the handler.
  • Mastery resilience: a per-target "fresh python subprocess" fallback is a cheap guarantee against process-level state bugs. Fits the SPEEDUP_PARALLELISM.md fan-out-then-join pattern exactly; promote target_solve_subprocess.py into _lib/ as a reusable helper rather than keeping it per-challenge.
  • Family bank: add axum_identity_delegation to kb/web_exploit_families.json so future Axum+identity_directory_route challenges fingerprint instantly.
  • Keep in clone vs. port to shared: the three real wins (status-recovery, URL base-rebuild everywhere, subprocess fallback) are shared-adapter changes — they help every web agent. The specific _tech_pass_the_identity fingerprint table also belongs in the shared battery (banked family). Only the per-attempt debug prints should stay in the clone.
  • Stall time: ~45 min, all of it on the Mastery 2/5 drop. Three failed mitigations (parallel retry, urllib direct retry, curl subprocess retry) all shared the same URL-folding bug; adding a single stderr debug print in the subprocess revealed it in one run. D+1: write a debug-first-not-mitigate-first lint into the AUTO-LOOP playbook ("print what the technique actually fetches before trying another retry strategy").
