Triage

Mobile-android lane. The claim-time per-lane autosolver (autosolve_mobile.compute) solved Single Solve directly from the APK bytes over the bearer GM, returning a backend answer code in the ANS-<16 hex> shape. Single Solve CORRECT at 13:00:04Z.

Investigation

Time Trial and Mastery would not start. Over the bearer-token GM (public HTTPS, the default path):

  • start <id>/time_trial -> HTTP 503 {"error":"training_rotation_invalid"}
  • start <id>/mastery -> HTTP 503 {"error":"training_rotation_invalid"}
  • retry -> 409 start_required
  • practice -> 405 operation_not_allowed

A prior session note (and memory) had called this "server-side, event-wide, unfixable." That was wrong. Reading the GM openapi POST contract showed these are dual-pool routes:

"regular untimed play is the default; run_for_time:true opts into a fresh timed Hall of Fame attempt."

So a timed route called WITHOUT run_for_time falls back to the UNtimed "training" pool, and that pool was exhausted/invalid -> the 503. It was never a global outage: the Day 08 binary lane's Time Trial start succeeded in the same minute (its training pool still had variants).

The fix is to opt into the ranked timed pool:

gm._post(op="start", challenge="mobile-android-day-08-cleartext-session/time_trial", run_for_time=True)

-> result CORRECT, variant_fresh True, ranked_attempts_remaining 32


Both Time Trial and Mastery provisioned a fresh variant and graded CORRECT. (On the base id with no
`/time_trial` suffix, `run_for_time:true` is rejected with `timed_intent_not_available`, confirming the flag
belongs only on the timed routes - single-solve/non-timed routes must not receive it.)

Minimal Reproduction

  1. Single Solve: claim -> autosolve_mobile computes the backend answer code from the APK bytes, submit.
  2. Time Trial / Mastery: start the /time_trial and /mastery routes **with run_for_time:true** (the untimed training pool is exhausted; the ranked timed pool is fresh). Solve each assigned variant from its own bytes and submit under the exact answer_ids; Mastery is a bundle (set1.answer, set2.answer, ...).

Lessons Learned

  • training_rotation_invalid on a timed start is a pool selection problem, not a server outage. Re-issue start with run_for_time:true on the same timed route.
  • Banked into challenges/_lib/ctf_gm.py GM.start(): it now auto-opts into run_for_time:true whenever a timed route returns training_rotation_invalid, so autosolve/fastpath inherit the fix.
  • Read the GM openapi before declaring something unfixable - the dual-pool contract was documented there the whole time.
