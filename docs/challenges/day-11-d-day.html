Self-heal: the root cause is fixed in the lane adapter, with tests

The Time Trial loss was not bad luck, it was an unbounded sleep inside a bounded window. Two changes in challenges/_lib/autosolve_binary.py make that class of failure impossible for this lane:

1. The timed window is now a hard budget. _window(start) parses the attempt's deadline into an epoch second and _left() reports what remains. _gm()'s 429 backoff now refuses to sleep past it:

nap = 0.6 + 0.15 * i
left = _left()
if left is not None and left - nap < _GUARD_SECS:   # _GUARD_SECS = 3.0
    raise Expired()      # never sleep past the deadline: give the untimed fallback a chance
time.sleep(nap)

Expired is the signal run() and autosolve.attempt() already understand, so a doomed ranked attempt is abandoned early - while a fallback can still get a variant - instead of being slept to death. An untimed attempt has no deadline, so _left() returns None and the original 429 tolerance is untouched. _run_once sets the window right after start and clears it in a finally, so a window never leaks into a later call.

2. A timed window is never opened into a storm. The clock starts the instant op=start returns, so _prewarm() first proves the GM is responsive with a call that costs no attempt and carries no deadline (op=status). Any answer - including a 409 start_required on an ungated Mastery route - proves responsiveness; only a persistent 429 means "still in the storm", and _gm's backoff absorbs that there, where there is no window to burn. Untimed routes skip the probe entirely and spend no extra call.

Root cause of the 409: the route is dual-pool, and the ranked attempt is one-shot

The 409s were not a pool outage and not a request-shape rejection. The GM's own openapi (saved locally as scripts/gm_openapi.json, fetched once) states the model:

run_for_time: "On a dual-pool route, true selects a fresh timed ranking attempt; omitted or false selects regular untimed play. Single Solve and legacy routes do not accept this property."

op: "practice is a legacy continuation operation; new dual-pool routes use start or retry without run_for_time for regular play."

So a timed route has two pools:

PoolEntered withSupply
Ranked (Hall of Fame)start + run_for_time:trueexactly one attempt per player per route
Untimed ("training"/practice)start / retry / practice, property omittedunique_attempts_remaining variants

And three behaviours combine into a trap:

  1. **op=start resumes, it does not create.** Once an attempt exists on the route, a plain start hands back that attempt - including a dead one, with result:"expired". It can never escape a corpse. This is why the "fallback to untimed" path could not rescue the mode.
  2. The ranked attempt is one-shot. A second run_for_time:true is refused with timed_intent_not_available. That error does not mean "the timed pool is unprovisioned" (the Day 09/10 reading); here it means "your one ranked attempt is already spoken for".
  3. **retry and practice draw from the same untimed pool**, and that pool is at 0 for this route, so both answer retry_variants_unavailable.

That closes every exit simultaneously, and because Mastery's prerequisite is a CORRECT Time Trial, the one lost 30-second window cost two modes.

The defect is our policy, not the GM. HUNTRESS_RANKED=1 spends the single one-shot ranked attempt as the unverified first touch of the mode, at the exact instant of the 09:00 release when all five lanes hammer the GM and any call can 429. Ranked-first is only safe when the ranked attempt is near-certain to convert; into a 30-second window during the release storm it is not, and the penalty for losing it is the deadlock above rather than merely a lost ranking.

One free call would have predicted it. op=status reports unique_attempts_remaining and costs no attempt. Pool depth varies wildly per route (15 for mobile day 11, 247-251 for binary days 1 and 10), so it has to be read, never assumed - and a 0 means a timed attempt there is a one-shot with no way back.

This is now written up for the whole fleet in docs/gm-facts.md, new section "THE 409 FAMILY ON TIMED ROUTES", with the error-to-meaning map, the rollout list for the other four lanes (autosolve.attempt() is the shared ranked-first call site; autosolve_script.py has the same unbounded in-window backoff at lines ~290 and ~516) and the agent-prompt changes. It also closes a question that doc had left open since 2026-10-07: yes, an expired attempt is still a free offline lab.

CORRECTION to the section above: D-Day's timed routes are LEGACY SINGLE-POOL, so there was no untimed fallback to lose

The section above describes the dual-pool model correctly as the GM's general contract, but it mis-classified this route. A later probe settled it. The decisive test is the one this playbook already prescribes for the Day 10 fix - send run_for_time:false as well as true:

start run_for_time:true   -> 409 timed_intent_not_available
start run_for_time:false  -> 409 timed_intent_not_available     <-- the tell

A genuine dual-pool route ACCEPTS false (it means "regular untimed play"). Rejecting false as well as true means the route does not accept the property at all, which the openapi states is the signature of Single Solve and legacy routes. So binary-reverse-engineering-day-11-d-collection-planner/time_trial is a legacy SINGLE-pool route: ranked and untimed are the same pool, unique_attempts_remaining counts that one pool, and the ranked attempt consumed its last variant.

Why this matters more than a labelling nit. autosolve.attempt()'s whole safety net is "if the ranked attempt fails, fall back to _run(False) - the untimed path - so the flag is still captured without Hall-of-Fame credit". On a dual-pool route that works. On a legacy single-pool route it is a no-op: the fallback draws from the same exhausted pool and gets the same 409, which is exactly why D-Day's Time Trial was not rescued. The ranked/untimed fallback cannot protect a legacy route, so on those routes the ONLY protection is not losing the window in the first place - which is precisely what the window-budget guard and the op=status prewarm do. The heal is therefore more load-bearing than it first appeared, not less.

Practical rules this adds:

  • Classify the route BEFORE relying on the untimed fallback. One free start run_for_time:false probe distinguishes dual-pool (accepted) from legacy single-pool (409). On a legacy route, treat the first timed attempt as the only attempt.
  • unique_attempts_remaining on a legacy route is the total remaining attempts, ranked and untimed together. A 0 there means the mode is finished for the day, not merely unranked.
  • Do not report "falling back to untimed to keep the flag" as if it were protection on a legacy route. It is a second request against the same empty pool.
  • Corollary for recovery: op=practice and op=retry are the only ops that can retire a dead attempt and provision a new one, and on a legacy route both draw that single pool. Polling them (one call per cycle, alternating) is the correct and only recovery - op=start will resume the corpse forever.

THE GM CALL BUDGET - which calls cost a variant, which cost nothing, and what actually drained the pool

Written for the agent instructions, because "do not hammer the GM so the pool is never drained" is the right instinct attached to the wrong mechanism, and the imprecise version would make agents avoid the one FREE call that prevents the whole failure.

What actually drained the pool on Day 11

ONE attempt start drained it - not many calls. The sequence was:

  1. All five lanes hit the GM simultaneously at the 09:00 release -> the GM answered 429 (this is the hammering, and it is self-inflicted).
  2. A ranked Time Trial attempt was opened with a 30 second deadline. That start consumed the challenge's last variant.
  3. The 429 backoff then slept through the entire 30s window -> the attempt expired unused.
  4. retry/practice could not renew it, because the variant it would need was the one step 2 had just spent.

So there are two separate defects, and an instruction must name both:

DefectWhat it costsThe rule
Hammering the GM at release (429 storm)the WINDOW - a 30s deadline slept awaynever let retry/backoff sleep inside a timed window; stagger lanes; prove the GM is answering BEFORE starting the clock
Starting an attempt speculativelythe VARIANT - one per start, non-refundableonly open an attempt when the solver is already proven and you are ready to submit within seconds

Hammering did not consume variants. Starting did. Fixing only one of the two leaves the hole open.

Which calls consume a variant, and which are free

GM callConsumes a variant?Notes
op=start (fresh)YES - onethe only way a new variant is handed out; non-refundable even if the window is wasted
op=retry, op=practiceYES - onethey retire an attempt and provision a replacement from the same rotation
op=start on an existing attemptnoit RESUMES; it cannot create or spend anything
op=statusno - FREEand it reports unique_attempts_remaining, the pool depth
op=listno - FREEsolved flags for the whole day in one call
op=openapino - FREEthe contract; cache it, it does not change
op=artifact / op=downloadno - FREEstill serves an EXPIRED attempt's bytes, and the Single Solve artifact
op=submitnobut it cannot revive an expired attempt - grading is gated on the deadline

**The practical consequence: read calls are free, so never ration them, and never ration op=status in particular.** One free op=status before any timed start reports unique_attempts_remaining; a 0 there means the attempt is a one-shot with no recovery. That single free call would have predicted Day 11's entire deadlock in advance. An instruction that discourages it is strictly worse than no instruction.

What "do not hammer" should actually say

  1. Never poll a write op in a loop. start/retry/practice each spend a variant when they succeed. Polling them is how a rotation gets drained for real. Poll op=status instead - it is free and it tells you whether a write op would even work.
  2. Do not open a timed attempt as an unverified first touch, least of all at the release instant. Prove the solver on the untimed Single Solve first, then open the window once, ready to submit in seconds.
  3. Stagger the lanes at release. Five lanes starting simultaneously is what produced the 429s; the GM is fine when approached one lane at a time.
  4. Treat the window as a hard budget. Never sleep past a deadline in backoff - abandon the attempt early instead, while a fallback is still possible.
  5. Cache what does not change - the openapi, the questions contract, artifact bytes - and re-read rather than re-fetch.
  6. When a mode is already dead, stop calling write ops. Read its state once, replay the saved bytes offline, and wait for the reset. Day 11's recovery polling was switched to a scheduled waiter that makes zero GM calls until the reset moment for exactly this reason.

Daily reset (user-confirmed 2026-10-11)

Every day there is a reset: all unsolved challenges and flags are reset. So an exhausted rotation is a lost DAY, not a lost challenge - which is both the reassurance and the reason the rules above matter. A drained pool cannot be recovered within the day by any means (every op, both transports and every request shape were measured on Day 11; see the sections above), so the only protection is not draining it.

18. "KEEP TRYING" DONE WITHOUT HAMMERING - the day is now covered end to end

User direction: "keep trying until GM finally is good to go for TT". The literal reading - retry the write ops in a loop - is the one thing that must not happen, because start/retry/practice each spend a variant when they succeed, and polling them is how a rotation gets drained for real (section "THE GM CALL BUDGET" in docs/gm-facts.md). op=status is free and reports unique_attempts_remaining, so the whole day can be watched at zero cost and the write ops spent only when there is something to spend them on.

The fleet had already built exactly this while this agent was working, which is the better outcome than building a second one: challenges/_lib/route_watch.py + catchup_timed.py, created 12:16-12:17 today.

This agent's two changes were to close the gaps around that watcher rather than duplicate it:

  1. The 23:50 -> 00:00 hole. route_watch stops at 23:50 by design; the rotation resets at 00:00 EDT. That settles the question in the title: the solver is not the blocker and never was. The blocker is that there is no gradeable sitting.

The new finding, and it is the organisers' side

That run also carried the GM's own guidance field, which is returned verbatim in every response for this challenge and which I had not mined closely enough. It says:

"For timed modes, start reconnects to the same attempt; only retry spends one of the unique_attempts_remaining. After all fresh variants are used, practice continues on the last artifact without a timer or Hall of Fame time and can still complete the mode."

That is a precise description of our exact state - all fresh variants used, unique_attempts_remaining = 0 - and it promises an untimed path that can still complete the mode. The attempt's own next_op field independently says **practice**. The saved openapi agrees: practice is "a legacy continuation operation", and its request body is just {op, challenge} with no other required property.

scripts/practice_contradiction.py therefore made one call per target with EXACTLY that documented minimal body - no client helper, no added properties, nothing our side could be blamed for:

POST {"op":"practice","challenge":".../time_trial"}  -> HTTP 409 {"error":"retry_variants_unavailable"}
POST {"op":"practice","challenge":".../mastery"}     -> HTTP 409 {"error":"retry_variants_unavailable"}
POST {"op":"practice","challenge":"<base>"}          -> HTTP 409 {"error":"retry_variants_unavailable"}

So the live GM refuses the operation it documents as the fallback for precisely this situation, and refuses it with an error about RETRY variants - for an operation documented as needing none. Three independent GM statements point at practice (the guidance text, next_op, the openapi description) and the fourth, the endpoint itself, rejects it.

Why this matters more than one challenge

  1. It is a GM-side defect, not a client error. Worth reporting to the organisers (Discord) with the three lines above, because it is reproducible, minimal, and self-contradicting on the GM's own wording.
  2. It explains the whole day honestly. The user's instinct throughout - "this means there is another way to solve, because they do not hard block us this way at all" - was correct: there IS a documented untimed way, and we were right to keep looking for it. It is simply not functioning on this route today.
  3. It retires a line from our own notes. docs/gm-facts.md records practice as a write op that "spends a variant when it succeeds". Per the organisers' guidance that is wrong for the post-exhaustion case: after the fresh variants are gone, practice is documented to continue on the LAST artifact without a timer, i.e. it is meant to need no variant at all. Our own measurement cannot tell these apart, because on this route it never succeeds.
  4. Tomorrow's agents should try practice EARLY on any exhausted route, and treat a retry_variants_unavailable from practice as a GM bug to report rather than as the end of the day. If it works on some other route, that is the untimed completion path for every lane, and it is worth knowing before 09:00 rather than after.
