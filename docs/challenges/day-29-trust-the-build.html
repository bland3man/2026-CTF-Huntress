Why HS autosolve returned gate_blocked (0 accepted) on first MM try

Agent-6's web_wip.py clone carried the SS/TT shape (which worked), but the per-target MM fan-out needed one specialised exploit per target. Our generic probes returned a hostname / case id string instead of a proof_<32 hex> value. The GM silently rejected the batch as gate_blocked.

Fix landed on 2026-10-29 as the D30-cutover HS additions:

  1. is_valid_web_proof() in autosolve_web.py enforces ^proof_[0-9a-f]{32}$ before GM.submit — rejects non-proof answers client-side.
  2. match_family() reads kb/web_exploit_families.json and routes per-target to the right exploit family based on robots/html fingerprints.
  3. iter_lfi_candidates() reads kb/web_lfi_candidates.json for ordered path probes.

Lessons + D+1

  • Submit-time proof-shape guard is a permanent-return change. Prevents any future web Mastery from burning an attempt on a wrong-shape answer. One-line fullmatch on ^proof_[0-9a-f]{32}$.
  • Per-CID clone needs family dispatch for multi-target MM. A generic probe sweep misses when each target wants a different exploit. The two kb/web_* JSONs now ride on main (WS authored, HS wired).
  • Push-to-VM-and-pull-back worked. The HS agent-7 Internal Affairs bundle gave the VM-side agent enough pattern to solve HS's stuck Trust the Build MM in ~18 s. Keep this escape hatch wired.
  • Keep in clone, port to shared when a second lane needs it. The LFI probe lives in _audit/VM_pull_20261029/Trust the Build/lfi_probe.py on HS; shared-port candidate for web_live_primitives.py after 10/30 if a second challenge needs an LFI primitive.
