GM prompt

A Roslyn C# script and an inline ASPX host act as a bridge that carries managed code back into the script corpus. Recover their layered configuration, resolve each static handoff, and work out where the bridge actually leads.

Today's layer

The archive is the usual script_inventory corpus (137 inert fixtures: ps1/js/vbs/bat/py/sh/php/lua/pl/rb/mof/proj/...). Two carriers were new: Roslyn C# script (.csx) and Google Apps Script (.gs). Both are self-describing in the established way (HUNTRESS_ANALYSIS_V1:<KIND>-<payload> marker plus a v=3|key=value|... descriptor), so the banked solve_poly_d8 descriptor path answered 1238 of 1249 fields at first contact - including every -attack field, because the descriptor carries attack= itself and needs no LANGS entry for the new extension.

The genuine gap was 11 fields, all from one member: host-aspx-inline-csharp-csharp-script.csx.

Root cause

That fixture is the title's "bridge": an ASPX page that carries the entire Roslyn script as one escaped C# string literal inside <script runat="server">:

<%@ Page Language="C#" %>
<script runat="server">
private static readonly string EmbeddedCsx_4e8084fd = "// HUNTRESS_ANALYSIS_V1:HEX-763d337c...7374616765\n#nullable enable\nusing System.Collections.Generic;\nstring descriptor_4e8084fd = \"763d337c...\";\n...";
protected string InertRequest_4e8084fd(string action) { return "modeled:" + action; }
</script><%= "inert-analysis-fixture" %>

Because the embedded newlines are two-character \n escape sequences and not real line breaks, the whole specimen is one physical line. solve_poly_d8.MARK (HUNTRESS_ANALYSIS_V1:([A-Z0-9]+)-([^\r\n'"]+)) therefore ran past the end of the hex payload and swallowed the host's own code (\n#nullable enable\nusing System...) until the first real " character. clean_payload could not rescue that capture, so desc_of raised ValueError: unpeelable, the file never entered poly_answers' kv map, and all 11 host-aspx-inline-csharp-csharp-script-* ids reported no file for <id> [] -> AUTOSOLVE HELD with nothing submitted. Every other host container (host-google-docs-sidebar-google-apps-script.gs, host-php-webshell-php.php, host-wsf-*, host-hta-*, ...) stores its marker on a real line, which is why only this one member failed.

Fix (one additive helper in challenges/_lib/solve_poly_d8.py)

desc_of now tries the literal source first and, only if that yields no descriptor, retries on an unescaped copy of the source, keeping whichever descriptor has more fields:

def _unescaped(s):
    """An ASPX inline-C# host carries the WHOLE specimen as one escaped string literal, so the real line breaks are
    two-character \n sequences and MARK's `[^\r\n'"]+` capture runs past the payload into the host's own code."""
    if '\\n' not in s or 'HUNTRESS_ANALYSIS_V1' not in s:
        return None
    out = s.replace('\\r\\n', '\n').replace('\\n', '\n').replace('\\r', '\n')
    out = out.replace('\\"', '"').replace("\\'", "'").replace('\\\\', '\\')
    return out if out != s else None

_desc_of_text holds the previous marker/split logic unchanged; desc_of is now the two-candidate wrapper. The guard (\n present AND the marker present AND the expansion actually changed something) keeps the path strictly additive - a file that already decodes is never re-read, so nothing earlier can regress.

Lesson for the lane

A host container that stores the specimen as an escaped string literal is a new failure shape, distinct from every earlier carrier: the payload bytes are all present and plainly hex, but the marker regex's newline class never fires because there are no real newlines. When desc_of reports unpeelable on a file whose hex payload is visibly intact, expand \n / \" escapes and re-match before touching the extractor tables. The two genuinely new languages (Roslyn .csx, Apps Script .gs) cost nothing at all - as predicted by the self-describing-fixture hypothesis, a new language is free while the descriptor keys are unchanged. Only the new container idiom needed code.
