What the Game Master does

The Game Master is the source of truth for the challenge ID, attempt, target URLs, questions, answer IDs, deadlines, accepted answers, and final result. CourseStack supplies the player's identity to the Homebase proxy.

Supported operations used here:

OperationRequest
List challengesGET http://[ip]/huntress-ctf-proxy?op=list
Start or reconnectPOST JSON {"op":"start","challenge":"<id>"}
Check attemptGET ?op=status&challenge=<id>
Submit answersPOST JSON {"op":"submit","challenge":"<id>","answers":{"<answer-id>":"<answer>"}}
Read API descriptionGET ?op=openapi

The proxy URL has no trailing slash. The included gm.py (not found in any source) (not found in any source) handles these requests and saves the full JSON response.

The Game Master OpenAPI document also describes POST {"op":"pair"} through the trusted proxy for a personal bearer used by direct HTTPS Game Master clients. That bearer is not required inside Homebase and is not a credential for the challenge target. See WEB_AGENT_GUIDE.md (not found in any source) (not found in any source) for safe use by external agents.

Read the start response before browsing. It gives the target URL or URLs and the exact answer_ids. start reconnects to the existing attempt; it does not create a new timer. A partial response such as {"result":"accepted"} means some answers were accepted; check accepted_ids and remaining. Only {"result":"CORRECT"} means the full attempt is complete. A correct response may include the flag and solved_by. The proof_<hex> string from a target is the submitted answer; the Game Master flag is the completion result. They are different values.

The Game Master guidance says web challenges have no downloadable artifact; each start returns one or more live sites in targets[]. Better workflow next time

  1. Start through the Game Master first. Save the full start JSON. Never reuse a target URL from a prior attempt.
  2. Read the whole response. Copy the question, answer_id, answer format, timer, deadline, and every target URL.
  3. Recognize the app before choosing a tool.
    • Directory listing/backup: inspect robots.txt (not found in any source), then follow links and download the exact file.
    • IDOR: find record IDs through the app's own routes; compare owner and authorization behavior.
    • SQL injection: identify the search parameter and prove the query returns a hidden row.
    • LFI: inspect the include parameter, confirm traversal with a harmless system file, then locate the challenge proof file and save the exact response.
    • SSRF: use only the target's advertised public fetch route and topology; confirm the internal request with the current user's record before requesting the other role's record.
  4. Use the smallest suitable solver. Python's standard library was enough: urllib for HTTP, http.cookiejar for sessions, HTMLParser for links, and json/regular expressions for extraction. A browser is useful for visual discovery and for a human-readable handoff; sqlmap or a large scanner was unnecessary here.
  5. Verify before submitting. Proofs in this challenge matched proof_[0-9a-f]{32}. A hostname, case number, or ordinary record value is not the proof. Use the exact answer ID returned by the current start response.
  6. Submit through the proxy and read the result. Save partial results, then submit remaining answers. Query status after completion.
  7. Keep the timer honest. Default TT/MM are regular untimed attempts. Request run_for_time:true only when deliberately doing a ranked timer run.
  8. Persist evidence while the target is live. Untimed web targets stop after inactivity, and a solved/expired target can return HTTP 410. Save proof, vulnerable path, response, and submission result immediately.

What blocked agent-7 and what fixed it

The supplied agent-7 autosolve log (not found in any source) is useful because the failures were mostly orchestration and adapter problems, rather than a lack of HTTP tools. Its assignment listed curl and jq, a shared web kit, and up to three parallel agents. The work used HTTP requests; a graphical browser was not required.

  • The generic lane did not dispatch web. The first autosolve pass explicitly reported there was no banked autosolver for lane web and routed to an unmapped handler. The adapter registry only knew web-exploitation.
  • Lane alias mismatch: the dispatcher saw web, while its adapter map only knew canonical web-exploitation. It sent the challenge to a generic unmapped path. The agent added alias-to-canonical dispatch and normalized the lane when matching the local assignment.
  • Incomplete assignment snapshot: several attempts refused to start because the local watcher had no complete SS/TT/MM list snapshot. The autosolver was configured not to fall back to a fresh Game Master list call, so the assignment/staging data had to be repaired first. The copied assignment contract itself showed n_questions:0 and listed a static single_0.bin (challenge artifact, not published), while the real web start response supplied dynamic questions and live targets[]. For this lane, the assignment snapshot was not a substitute for the current Game Master start response.
  • Windows text encoding: one import failed because the Windows charmap codec could not encode the 🌐 challenge name in the file path. Running from a UTF-8 environment or setting Python's UTF-8 mode avoids this path/console encoding failure.
  • Targets were not always ready on the first response: the agent's debug records show an early response with questions but no targets[], followed by a ready response containing all five targets. A robust runner waits for the target list; it must not treat “no targets yet” as a solved or empty challenge.
  • Already-correct start response: SS and TT were already CORRECT for teammate. The generic mode runner treated a GM.start() response with result:"CORRECT" like an unsolved assignment and waited for answer fields. It needed to short-circuit as complete.
  • Artifact-only readiness assumptions: web starts have live targets and proof-N answer IDs, but no downloadable bytes. The agent marked proof-shaped answer IDs as discoverable by the web lane so the prebrief coverage gate could proceed to live target extraction. The saved TT residue shows the old gate held the attempt with proof-1 unresolved and zero extractors; it had not opened a target window at that point.
  • Misapplied route metadata: a generic LFI handler prepended the randomized routes[].path value to the origin and got 404s. For these apps, routes such as /handbook.php (reference kept as plain text; not an eligible file type), /explore, and /api/clues are at the target origin. Probe the actual app routes at the assigned host root; do not assume a routes[] path is a URL prefix.
  • No challenge-specific battery: the general web solver did not combine these five different patterns. The agent added one per-challenge technique that mapped Target 1 through Target 5 and returned the first proof it found.
  • Mode sequencing and attempt reuse: the agent did not need to open a new ranked TT attempt because TT was already solved. Mastery already had active shared attempt [id]. The agent correctly kept that attempt and did not spend a new variant with retry.
  • Evidence was not persisted: the agent's technique returned the proof to the submit pipeline, but its log recorded only CORRECT and the flag. It did not save the Target 4 answer or response body. The local solve_mastery.py (not found in any source) now writes answers-mastery.json (not found in any source) and each target's result before submission; keep that output.

The log contains several held or blocked passes before the final successful rerun. Early attempts were gate-blocked after 7.8 and 93 seconds; later passes spent about 95–98 seconds blocked on Mastery before the per-challenge technique completed. The last autosolve pass completed the existing MM attempt in 18.2 seconds; the attempt itself had been active since 13:11:54 UTC. The path used for Target 4 was ../../../run/huntress/objective.txt (not found in any source). SS and TT were already credited to teammate; the 18.2-second agent result refers to MM only. The agent's autosolve summary has null flags for those already-solved SS/TT entries; use the saved Game Master status files for their actual flags.

Why the web agents need a coordinator

A prompt alone does not give an agent network access or Game Master authority. The agent runtime must expose a browser/HTTP tool that can reach the assigned Huntress target, and the coordinator must be able to call the Homebase proxy. Keep those roles explicit:

  • The coordinator starts/resumes SS, TT, or MM and provides the newly returned URL, exact question, answer ID, format, and timer.
  • A browser worker investigates one target and returns the proof, path/route, and response excerpt. For MM, independent workers can handle separate targets; Target 2's worker must keep its own cookie jar.
  • The coordinator rejects malformed or unsupported answers, writes the answers object, submits through the proxy, and checks status.

Common reasons an agent stops short are stale target URLs, no browser/network capability, confusion between the Game Master bearer and the target site, stopping after identifying a vulnerability instead of recovering its proof, losing a target's session cookie, or submitting the right value under the wrong answer ID. The handoff script and gm.py (not found in any source) checks address these failure points.
