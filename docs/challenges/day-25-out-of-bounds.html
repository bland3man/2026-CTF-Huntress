The genuinely new structural wrinkle is the cross-member equality precondition on the four d25_analysis_config_* slots. The GM's own question text spelled it out:

Decode both d25-- role members and require their config objects to be byte-for-byte equal before using the common value.

So the vulnerable and the corrected twin carry the same HCFG config; the pair exists to be compared, and the four "shared" slots are only answerable once both decodes agree. The four corrected_config_* slots are the same four keys sourced from the corrected member alone - which is why both groups returned identical values.

HCFG extraction path (unchanged spine, Java container)

Per the GM's guidance, for a JAR:

  1. Parse every classfile constant pool in the JAR.
  2. For Base64-alphabet UTF-8 constants of at least 80 characters, Base64-decode.
  3. Accept the first CRC32-valid HCFG record.

HCFG record layout (constant across all 25 days):

0..3   ASCII "HCFG"
4      version
5      one-byte XOR key
6..7   little-endian payload length
8..11  little-endian CRC32 of the DECODED payload
12..   payload

XOR every payload byte with the key, verify CRC32, parse the decoded UTF-8 as JSON, read the top-level property. This is the same record the lane has decoded since Day 01; only the carrier changed (Day 06 Java constant pool, Day 16 wasm data section, Day 25 Java constant pool again, in a role pair).

Why this needed zero new code

challenges/_lib/autosolve_binary.py (2355 lines) contains no vulnerable / corrected / role-pair logic and did not need any. Two already-banked generic mechanisms covered the day:

  1. **_Q_MEMBER_PATS member resolver** (autosolve_binary.py:1398-1406) - built on Day 21 for "Use the unique d21-- member whose basename ends plugin.cmxs." It honours a basename-tail token only when the token contains a dot and exactly one member's basename ends with it. vulnerable.jar and corrected.jar are exactly that shape, so each role slot bound to the right member with no new case.
  2. The by-name fact route - a slot whose field name matches a binary_facts fact name is answered SURE from the parsed facts (container class, SHA-256 by index, HCFG keys).

That is the whole reason the day went clean on first touch: today's "new layer" was a new naming convention over already-modelled structures, not a new structure. Recognize, then reuse.

Findings, confirmed hypotheses, and what could be better

Finding 1 (pipeline defect, affects every lane): outcome.json records ERROR:no_outcome on a clean sweep

All four Day 25 lanes finished with every mode CORRECT, yet all four _board/*.outcome.json files record "outcome": "ERROR:no_outcome", "detail": null:

binary-reverse-engineering-day-25-...     outcome= ERROR:no_outcome
metadata-forensics-day-25-hive-mind       outcome= ERROR:no_outcome
mobile-android-day-25-integrity-signals   outcome= ERROR:no_outcome
warmups-day-25                            outcome= ERROR:no_outcome

The claim digest showed the matching symptom in-line: AUTOSOLVE ALL: autosolve printed no outcome line then AUTOSOLVE OUTCOME: ERROR:no_outcome, immediately after three AUTOSOLVE <mode>: CORRECT lines and an AUTOSOLVE NEXT: every mode of this challenge is CORRECT line. So the per-mode results were correct and only the summary line was missing or unparsed.

Why this matters beyond cosmetics: the lane FAILURE HISTORY block in the claim digest is built from these outcome records. The binary lane already boots with error-other [OPEN] seen Day 12,17 (2x) - Unclassified adapter error: read the traceback tail. A perfect day that self-reports ERROR:no_outcome will keep inflating that counter and send tomorrow's agent chasing a traceback that does not exist. The authoritative success record is _board/<id>.autosolve.json (per-mode result + flag) plus done.json; the outcome file disagreed with both. Recommend fixing the outcome-line emit/parse in the autosolve-to-claim_next handoff, and until then treating ERROR:no_outcome as "unknown", not "error", when building the failure history.

Finding 2: the ranked first-touch 409 is no longer reproducing

The lane's timed-start-409 [FIXED 2026-10-10] entry (6 occurrences across Days 09-12) did not recur. Both timed starts were accepted ranked on the first plain call, came back hall_of_fame_eligible: true, and neither submit consumed a unique attempt (TT 63 -> 63, Mastery 15 -> 15). The fix is holding on a Day-25-era route.

Finding 3: timed windows are server-provided and much wider than the rehearsed assumption

Observed windows were not ~30 s. Time Trial gave 80.3 s (submitted with 72.8 s slack) and Mastery gave 595.6 s (submitted with 545.0 s slack, including nine ~35.7 MB downloads). The lane's timed-slot heuristic is tuned to TT 18s; that bound is conservative by roughly 4x on this route. Keep reading the deadline from each start response rather than planning against a fixed 30 s, exactly as the standing rule says.

What could be better for this lane's category

  1. The candidate list missed today, and the miss was predictable. The digest said "no predicted candidate matches today's ids/artifacts/fields - treat today's layer as UNPREDICTED". Every prepared candidate was about new content (unasked HCFG keys, record geometry, PE/ELF header fields, new toolchains, malware id). Day 25 instead varied member selection: a two-member role pair inside one day prefix. Recommend adding a member-layout axis to NEXT-LAYER CANDIDATES - role/twin pairs (vulnerable vs corrected, before vs after, packed vs unpacked, debug vs release), N-member sets, and cross-member preconditions - since Day 15 (symbolized+stripped pair), Day 16 (direct+compact wasm pair) and Day 25 (vulnerable+corrected JAR pair) are now three instances of the same axis while the lane still models novelty as a content question.
  2. Cross-member preconditions deserve a first-class handler. Today's shared-config slots said "require their config objects to be byte-for-byte equal before using the common value". It happened to pass, so a solver that ignored the precondition and read either member still scored. A future variant that makes the twins differ would silently reward the wrong member. An explicit equality check (and a Hold when it fails) would convert a latent wrong-answer risk into a visible residue entry.
  3. The theme/question gap is worth keeping prominent. "Out of Bounds" plus "Prove the bounds error is real, trace its reachability" strongly implies vulnerability analysis; the graded slots asked for hashes, container tokens and config strings. Reading the narrative prompt as the task would have burned the untimed window decompiling Java for a CWE nobody asked about. The standing instruction to follow the GM's own per-question text over the title/prompt narrative paid for itself here.
  4. No artifact is retained for this lane. Autosolve streams evidence.zip and nothing lands on disk, so post-hoc verification depends entirely on the GM record plus the accepted hashes. Keeping one copy of the Single's zip (untimed, already downloaded) would make a disputed field re-checkable without a refetch.
