Protocol reconstruction

Single Solve framing

The APK asset huntress_puzzle.json contains the packet bytes:

48 41 14 41 4e 53 2d 36 30 31 44 33 39 30 36 42 42 35 38 38 35 41 43 11

The framing is 48 41 | length | payload | 11: 48 41 begins the frame, 14 is the payload length in hexadecimal (20 bytes), the 20-byte ASCII payload is the answer, and 11 closes the frame. Strip framing only after honoring the length; the decoded answer is AnswerANS-601D3906BB5885AC.

Time Trial protocol

I inspected the DEX methods called by Release.code() and evaluated the actual bytecode. Release.token() applies mixPacket02, then sessionSession08, then mixNonce57. The session routine processes seven frames in sequence. Each frame includes message type 0x15, the nonce selected for that round, and the one-based round number. The next nonce index depends on the rolling state after the current frame; the supplied order table therefore must be followed as state changes. Reordering the nonce bytes or treating them as an unordered set changes the result.

The final code path applies Mix.f1, then Util.finSession63, XORs the embedded 64-bit constant, and renders all 16 nibbles as uppercase hexadecimal after ANS-. The DEX interpreter preserves Java's signed shifts and 64-bit wraparound while following that call chain.

Mastery variants

The 12 deliveries use different versions of the same app-to-backend exercise. Their Release.code() methods lead through varying helpers for probes, trust checks, nonce/session state, and frame handling. I ran the assigned APK DEX instructions themselves so each delivery's constants, loops, branch decisions, and 64-bit arithmetic remained intact.

Delivery 11 is an .apks split package. Its base APK reads huntress_feature.bin from the feature APK, then assembles the two eight-byte values in byte order before continuing the release calculation. The solver reads the feature asset from the supplied split bundle and preserves that ordering.

The hardcoded client_secret and proof URL in the public app are request plumbing, not the answer. The accepted answer comes from the APK's release calculation (or, for Single Solve, the framed packet payload).

Reusable scripts

Files in this directory:

  • solve_dex.py interprets the DEX release method in APK and APKS files.
  • fetch_artifacts.py downloads the current assignment through the supported proxy and prints each SHA-256.
  • submit_answers.py submits a JSON answer map through the proxy.
  • requirements.txt pins Androguard 4.1.4.
  • answers_single_solve.json, answers_time_trial.json, and answers_mastery.json preserve the submitted answer maps.

Set up and use the tools:

python3 -m venv .venv
.venv/bin/pip install -r work/protocol-reconstruction/requirements.txt

.venv/bin/python work/protocol-reconstruction/solve_dex.py path/to/assigned.apk

For a mastery assignment with 12 deliveries:

.venv/bin/python work/protocol-reconstruction/fetch_artifacts.py \
  mobile-android-day-28-protocol-reconstruction/mastery \
  work/protocol-reconstruction/new_mastery --deliveries 12

for apk in work/protocol-reconstruction/new_mastery/delivery_*; do
  .venv/bin/python work/protocol-reconstruction/solve_dex.py "$apk"
done

Keep the output order aligned with the delivery numbers, then batch-submit all answers in one request:

.venv/bin/python work/protocol-reconstruction/submit_answers.py \
  mobile-android-day-28-protocol-reconstruction/mastery \
  work/protocol-reconstruction/answers_mastery.json

For a later attempt, first use the answer_ids, artifact filenames, and delivery count from that attempt's start response. Single Solve and Time Trial have one artifact each; Mastery uses delivery=0 through delivery=N-1. Compare local hashes with the SHA-256 values returned by the Game Master.
