The actual trick (Target 4 only - see Mastery note below)

The Worker's "trust check" on the forged-webhook target accepts any POST to the feature_route in /api/clues whose JSON body carries the expected event_type and owner_scope AND a bundle of self-asserted trust flags. No cryptography, no signature, no header gate - the only check is a shape test over a set of fields the attacker fully controls.

Mastery is a mixed bundle, not four copies of this. User-confirmed 2026-10-26 after seeing our runner: the four Mastery targets each expose a DIFFERENT web vulnerability class:

  • Target 1: archive-path exposure (recovery pending at writeup time).
  • Target 2: reference-only case exposed through its public API (IDOR-shaped).
  • Target 3: hidden record retrievable via boolean search injection.
  • Target 4: forged webhook via the trust-bomb body described below.

Running a single technique across all four Mastery slots is WRONG - the trust-bomb only clears Target 4. Luna 6 is automating Targets 2/3/4 while tracing Target 1.

Minimum body shape Luna confirmed works (flat + nested + spread, over-asserted on purpose so the exact necessary field is not isolated):

{
  "event_type":"case.promoted","type":"case.promoted","event":"case.promoted",
  "owner_scope":"executive","scope":"executive","owner":"executive",
  "actor":"analyst","role":"analyst",
  "signature_valid":true,"is_valid":true,"is_trusted":true,"trusted":true,
  "verified":true,"webhook_verified":true,"authenticated":true,"authorized":true,
  "approved":true,"source_trusted":true,"signature":"valid","event_id":"evt-1"
}

Server replies 200 with {"ok":true,"effect":"forged_event_consumed","evidence":"proof_<hex>"} on first POST. Submit evidence under the matching proof-N id.

Why this CLI commander lost the race

  1. Depth before breadth. The pre-dispatch notes (preserved verbatim at Trust_the_Webhook_Attempt_Notes.md) covered 16 families: HMAC with 30+ secrets x 25+ headers x 6 encodings, every JWT trust bypass, BadHost CVE-2026-48710, timing side-channel, path tricks, prototype pollution, SSTI, SSRF, CloudEvents, request smuggling. The one family it did NOT run was the simplest: a single flat+nested bundle of every plausible "trusted/verified/approved/signature_valid" flag at once. Each flag was tried individually and in small combos; never flattened + nested + spread as one body. That is a specific simplest-first gap in the web solver library.
  2. Decoy from the GM response. start.routes[].path returned a different hex route per attempt (/90708e67...c696/). The commander and the specialist both wasted probes on it before confirming it 404s on the live target. The actual route is the one /api/clues.feature_route reports and is the ONLY route to POST to.
  3. "Pure CF Worker" conclusion closed off attack families prematurely. Server-Timing header cfOrigin;dur=0 was read as "no Starlette, so no Starlette-shaped bugs apply." The real target still accepts a Starlette-shaped forged event by content alone - the framework label in /api/clues is thematic AND actionable.
  4. Mastery runner regressed. On the first Mastery run, /api/clues fetch for Target 1 and Target 3 hit the 30 s poll limit while provisioning; Python's pool.map propagated the first exception and killed the whole batch instead of isolating per-target. Fixed on the second attempt (90 s poll, cf.as_completed with per-target try/except) - Target 4 completed, Target 1 and Target 3 still never finished /api/clues within 90 s on the second attempt either. The CF edge appears to serve /api/clues lazily for some mastery variants; a working runner has to poll **GM op=status for targets[] readiness** rather than hammer the Worker edge directly.

Lessons applied today (code TODO; see commander repo)

  1. Mastery can be heterogeneous. Each proof-N on a Web Mastery may be a DIFFERENT web class (archive-path, IDOR, boolean sqli, forged-webhook). Do not run one family across all N; recognise per target via /api/clues and dispatch per family. The web solver's Mastery driver must call the lane classifier per target and pick a solver per target - NOT reuse the SS/TT solver verbatim for every slot.
  2. **Add a web_solvers.LADDER family webhook_trust_bomb** - trigger whenever /api/clues returns a JSON object with an event_type, a *_scope, a current_role, and a feature_route. Build the body with every boolean trust-flag flat + nested + spread, POST, extract evidence|proof|value|flag. This is the TARGET-LEVEL family, invoked per target when its clues match the pattern; still only one of several families Mastery needs.
  3. Add families next, in order of expected per-day frequency: archive_path_exposure (Day 02-style robots.txt + backup/.bak enumeration), idor_reference_only (sibling-id enumeration against a reference-only case endpoint), boolean_search_injection (classic ' OR 1=1--, length-oracle, UNION-based). The Luna 6 handoff names these three as the other three Mastery targets today, so Days 29-31 will almost certainly reuse the same template.
  4. **Mastery target readiness must poll op=status for targets[].** The Worker returns 404 or hangs during provisioning; the GM status response flips the target to a usable URL once the Worker is live. Our two Mastery runs today lost >90 s per target waiting on /api/clues directly.
  5. Trust the GM-authoritative route source first. start.routes[].path is a GM metadata echo (route catalogue for the whole lane, not THIS target) and is dangerous to probe. The only route to POST to is /api/clues.feature_route for the forged-webhook target, and will be different per other-family targets.
  6. Day-29/30/31 web template reuses this exact scaffold (Huntress Admin confirmed). Pre-built attack now exists for 1 of 4 Mastery families; the three others are high-priority prebuilds before the 2026-10-29 release.
  7. Decoy field in GM start response - start.routes - add to kb/false_signals.md so no future web lane burns time on it.
  8. Depth-before-breadth web failure mode. 16 attempted attack families across two commander machines over multiple days, and the one gap was the simplest flat+nested+spread "trust bomb". Add a simplest_first audit stage to every web lane solver: if the response grants on a plain content-shape test, EVERY cryptographic family that follows was wasted budget.
