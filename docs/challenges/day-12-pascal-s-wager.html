The challenge

Day 12 is the twelfth rotation of the lane's single stable schema. The toolchain changes every day (C, C++, .NET, Go, Rust, Java, Kotlin, Swift, Nim, Zig, D, and today Delphi/Pascal - the title's wager), but the questions never do: a multi-field forensic inventory over a cumulative evidence bundle, where each day adds one more dNN deliverable to the same archive.

What actually cost the day: the timed routes

Coverage was never the problem. The loss was operational, and worth recording precisely.

At claim time, three agents plus the lane manager hit the Game Master simultaneously and it answered 429 rate_limited. The Time Trial's op=start had already opened its 30 s window, so the client's own 429 backoff ran into the deadline and ctf_gm.WindowExpired fired with the honest message:

timed window: 4.4s left, a 4.0s backoff would not leave 3s for download+solve+submit

A free op=status read then showed the route was unrecoverable:

{"result":"expired","unique_attempts_remaining":0,"hall_of_fame_eligible":false,
 "mode":"time_trial","next_op":"practice"}

The organisers' own rules (docs/official/README.md, rule 5) say that once a route's rotation is spent, op=practice is an untimed continuation and a CORRECT practice submission can still complete the mode. That made one attempt strictly positive-EV: the attempt was already expired, ranked eligibility was already false and the pool was already 0, so there was literally nothing left to lose. The result, measured:

op=practice  -> 409 {"error":"retry_variants_unavailable"}
op=mastery start -> 409 {"error":"prerequisite_required"}

So the GM answers with a state its own documentation does not list for this situation (retry_variants_unavailable, where the published rule describes rotation_exhausted), the documented escape is refused with that same 409, and Mastery is correctly gated behind a Time Trial that can never become CORRECT. No client call fixes this - it is a GM-side state, identical to the Day 11 D-Day deadlock already on record. Both 409s handed out no variant, so nothing further was spent; the Mastery pool is still intact if the route is ever reset. Escalated in _board/agent-2.needuser.

Framework changes made (minimal, tested)

Three narrow fixes, all of which only ever trigger on a GM state measured live today:

  1. **ctf_gm.py: added GM.practice().** The op was already in TIMED_WRITE_OPS and governed by the gate guard, but the client had no method for it, so the documented rule-5 escape was unreachable in code.
  2. **autosolve_binary.py: _first_op(pre, cid).** When a free op=status read already says the current attempt is finished and the GM itself names next_op=practice, the one authorised timed write now goes to op=practice instead of op=start. This matters because op=start on a dead attempt only resumes it - but it still answers, so the client counts the gate pass's single write as spent, and the op that would actually help is then refused. The verdict is keyed by challenge id, which was a real bug I introduced and then caught live: op=status raises on an unstarted mode (409 start_required) and therefore records nothing, so an unkeyed module global handed the Time Trial's "expired, next_op=practice" verdict to Mastery, which sent op=practice where op=start was correct. That cost one wasted 409 and is now a regression test.
  3. **autosolve.py: _gm_side_dead(err).** "Our solver was not ready" and "the GM has no variant left" are opposite situations and were being treated alike. A Time Trial that is dead from GM-side exhaustion no longer blocks a Mastery attempt - Mastery keeps its own readiness gate, and a genuine ordering gate costs only a free 409 prerequisite_required. Without this, a mode we were measurably ready for would have been skipped on an assumption rather than on the GM's own answer. (Today the GM's answer was a real prerequisite, so the outcome is unchanged - but it is now established by measurement, not by guesswork.)

Lessons for tomorrow

  • The lane's hypothesis holds again at n=8: a new toolchain adds zero or one new slot. Day 11 (D) and Day 12 (Delphi) both added none. Do not budget analysis time for the new runtime - budget it for the clock.
  • The 30 s window, not the binary, is the scarce resource. A ~32 MB artifact plus 120 fields is ~2.2 s of compute; the entire Day 12 loss came from a release-time 429 storm colliding with an already-open window. The readiness gate correctly said READY both times - readiness was never the failure mode.
  • A route that reads unique_attempts_remaining: 0 with an expired attempt is finished, whatever next_op claims. It is worth exactly one call to confirm (nothing can be lost), and then it is an organiser request, not an engineering problem.

Appendix: the 100% offline prediction for both timed modes

A timed attempt serves mutated bytes, so no table of remembered values is honestly a "prediction". What can be made 100% was made 100%, by scripts/predict_timed.py (RESULT: PASS), in three parts:

(a) Frozen, submit-ready answer sets - exact if a reset serves variant-000 again:

FileContentsTime
scripts/predicted_time_trial.json120/120 fields2.29 s
scripts/predicted_mastery.json360/360 fields (3 x 12 x 10)6.33 s

(b) Derivation proof - what makes it 100% for any variant. Each member's HCFG record was rebuilt as a synthetic variant with a new single-byte XOR key, new campaign/domain/mutex/url, and a different payload length so the record physically moves - which shifts hcfg_offset, the slot most likely to be faked by a memorised value. The extractor had to return exactly the injected truth: 12 synthetic variants x 8 fields, all PASS (campaign, domain, mutex, url, xor_key_hex, crc32_hex, hcfg_offset, hcfg_version).

Honest limit: **d01 and d11 were SKIPPED** - their record is not stored raw (it hides in a wrapper: base64 text or a dedicated section) and the synth harness only rebuilds raw records. The extractor reads both correctly (they scored 100% in (a)), but the mutation proof does not cover those two wrapper paths. That is a gap in the harness, not a demonstrated gap in the extractor, and it is recorded rather than glossed over.

(c) Field classes (scripts/field_classes.json) - of the 120 Time Trial ids, 40 are variant-INVARIANT and already certain for any variant (format elf/jar/pe_cli, architecture+machine x86-64 and i386 for the .NET PE, elf_class 64, elf_type ET_EXEC, endianness little, has_symtab/has_cpp_typeinfo/has_cpp_vtable/ has_hcfg_section true, hcfg_version 1, compression_methods [0,8], metadata_version v4.0.30319), and 80 are variant-DERIVED, recomputed from the attempt's own bytes (sha256, config crc32, xor key, hcfg_offset, campaign/domain/mutex/url, entry point, section names, symbols, disassembly).

Net: given a window, the submit is immediate and the content is proven rather than hoped for.

Why they were lost at 09:00 and why they came back. The 09:00 Time Trial was a one-shot for the team (unique_attempts_remaining 0); its submit landed inside the Game Master's refusal window (first 429 about 20 s after the release) and the 30 s clock ended. The organizers later said staff testing had drained the shared pregenerated pool and that the "continue in practice" route, rejected earlier (retry_variants_unavailable), was fixed. At 16:04 the GM's own free status read {expired, unique_attempts_remaining 0, next_op practice}; the adapter's single write went to op=practice (answered 200, practice: true, no deadline), the solver read 120 fields from the delivery in 5 s and the submit was CORRECT.

The held Mastery field. The first Mastery attempt (a fresh 30 s window right after the Time Trial) accepted 359 fields and held back set2.d10_analysis_machine on purpose (no guess was sent). The three deliveries were saved (the adapter now keeps the bytes of any attempt that does not end CORRECT). Offline: sets 1 and 3 carried a Linux ELF for Day 10 (e_machine 62, answered x86-64, accepted), set 2 carried a native Windows PE (d10--variant-001.exe, COFF machine 0x8664). The contract for that field says "a normalized architecture name, a standard tool or symbolic label, or the equivalent decimal or hexadecimal machine code is accepted"; the Day 10 live record in autosolve_binary.py says the ELF token x86-64 was rejected for the PE variant and that the raw machine code as a base-10 integer was what the grader wanted. So the PE answer is 34404 (0x8664). One sure answer, no spelling probes. Replaying the saved deliveries through the updated adapter gave 360 sure, 0 probe, 0 unknown; the second (practice) Mastery draw was solved in one submit.

Lessons. (1) A timed attempt that ends without CORRECT must keep its bytes (done: _save on any failure). (2) A mixed ELF/PE delivery changes the accepted answer form of header fields; read the contract's accepted forms and prefer the numeric machine code for a PE. (3) The catch-up decision catchup_timed.decide returns NO-GO whenever unique_attempts_remaining is 0, so it never tries the practice continuation that the GM offers (next_op: practice); run the gated autosolve.py directly for that case. (4) Wait for the organizers' fix; never burn attempts to force it.
