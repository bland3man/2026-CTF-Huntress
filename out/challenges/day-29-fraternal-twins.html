What was new

The pair is a NEW member-tag family the shared autosolve_binary.py had not seen: the two binaries carry compiler-optimization-level tags in their filenames (-O0 / -O3), while the GM asks the pair-selector questions under the SEMANTIC member tags unoptimized / optimized. The existing _variant_tags() helper derived the tags straight from the filename (o0 / o3), so every d29_analysis_optimized_* and d29_analysis_unoptimized_* id went unresolved.

Fix in the per-CID solver clone

Only this challenge's own solver copy was patched; shared lane kits were left untouched. challenges/Day 29/⚙️ Fraternal Twins/scripts/binary_wip.py

  1. _variant_tags() now additionally emits the semantic aliases "unoptimized" for a member whose filename matches [-_]O0(?:[-_.]|$) and "optimized" for a member whose filename matches [-_]O([123s]|fast)(?:[-_.]|$). Both are registered only when the dNN actually contains such a named member, so no other day picks them up by accident. The existing o0 / o3 tags from the normalised filename are kept, so questions that happened to ask under those names still work.
  2. The clone registers itself under sys.modules["autosolve_binary"] at load time. The runner's own _load_adapter already loads the clone as solver_copy_binary_reverse_engineering, but prebrief's release_scan imports autosolve_binary by name, so without the sys.modules binding the clone's new aliases are invisible to the prebrief gate and the gate HELDs on fields the clone itself can answer. The binding is additive and scoped to the runner's own process; nothing else is modified.

Reuseable lesson

A per-CID solver clone's patches are only visible to code that goes through the runner's _load_adapter path. Prebrief, release_scan and anything else that calls importlib.import_module("autosolve_binary") sees the shared adapter unless the clone pins itself under that name in sys.modules at load time. For additive patches that need the prebrief gate to pass, the one-line sys.modules["autosolve_binary"] = sys.modules[__name__] at the top of the clone (after its own imports) is enough; it is scoped to the runner's process and leaves the shared file untouched.

For the pair-member tag family: future day-pairs that carry structural tags in their filenames (gcc/tcc, family-a/family-b, symbolized/stripped, direct/compact, O0/O3) can keep working the same way as long as _variant_tags() can derive the tag the GM asks under. When the GM asks under a SEMANTIC tag the filename does not literally spell (optimized/unoptimized vs -O3/-O0), add a bounded alias in _variant_tags() keyed to the actual filename substring; keep both the raw and the semantic tag so a future question in either naming still routes.
